간략 소개

'시킨 일'이 아니라 '풀어야 할 문제'를 먼저 보는 개발자, 박진국입니다. 2019년 고등학교 졸업 직후부터 7년간 백엔드 서버를 설계·구축·운영해왔고, 같은 기간 학업을 병행해 컴퓨터공학 학사와 국민대학교 인공지능전공 석사를 취득한 'AI를 다룰 줄 아는 백엔드 개발자'입니다.

Spring Boot·Java·Kotlin 기반의 서버 개발을 주력으로, DDD·Hexagonal·Clean Architecture를 적용한 RESTful API 설계와 PostgreSQL·MySQL 데이터베이스 모델링, Docker·Kubernetes 기반 컨테이너 운영과 CI/CD까지 서비스의 전 주기를 직접 책임져 왔습니다. 총 회원 10만·MAU 2.8만 규모 서비스의 리뉴얼과 운영을 맡으며 대용량 트래픽에 견디는 분산 아키텍처, 운영 중 쿼리 최적화, 24시간 운영 안정성을 실무에서 다뤘습니다. Spring Boot를 가장 오랫동안 사용했지만 프레임워크 매커니즘에 대한 이해를 바탕으로, Ktor, Nest.js, Flask 등 다른 어떤 환경에도 빠르게 적응할 수 있습니다.

저는 반복·정형 업무는 자동화하고 사람은 더 중요한 문제에 집중해야 한다는 생각으로 AI 코딩 도구(Claude Code·Cursor 등) 및 Third-Party 프로그램을 적극 활용해 개발·운영 생산성을 끌어올립니다. 주어진 작업만 처리하기보다 비즈니스 목표와 기존 시스템 영향도를 함께 고려해 스스로 우선순위를 판단하고 주도적으로 움직이며, 작은 팀에서 기술 선정·환경 구성·일정 조율까지 맡아 팀장이 믿고 일을 넘길 수 있는 역할을 해왔습니다. 맡겨지는 범위가 커질수록 그만큼을 책임지고 완수하는 것을 강점으로 삼습니다.

저는 이렇게 일합니다

  • 빠른 습득력과 업무 능력을 믿기에 변화를 두려워하지 않습니다.
  • 다른 직군의 동료와도 명확하고 솔직하게 소통하고, 문제 상황과 처리 계획을 이해하기 쉽게 투명하게 공유합니다.
  • 업무의 본질적 필요성을 먼저 고민하고 개선안을 제시해, 더 나은 결과물을 도출하는 데서 보람을 느낍니다.

핵심 역량

  • 백엔드 설계·구축: DDD, Hexagonal, Clean Architecture 기반 RESTful API 설계와 데이터베이스 모델링을 직접 수행.
  • 대용량 운영·성능을 고려한 설계: 대용량 트래픽을 고려한 분산 아키텍처(Docker/Kubernetes, ECS Auto Scaling, RDS Read Replica), 캐시·CQRS 적용, 쿼리 최적화·인덱싱으로 운영 중 서비스 성능을 개선. 피크 시간대·비상대피 등 트래픽 급증 시나리오 부하테스트 설계.
  • LLM 응용·활용: 같은 모델이라도 프롬프트 설계와 출력 검증·정합성 보정, 용도에 맞는 파이프라인 조정으로 결과 품질과 신뢰도를 개선. 입력 전처리 → 구조화 출력(JSON) 파싱·검증 → 출력 후처리·정합성 보정으로 비결정적 LLM 출력을 운영에 쓸 수 있는 수준으로 다듬어, Gemini·Grok·OpenAI 등으로 PDF 문제 적재(수작업 80시간 → 20분)·콘텐츠 생성을 안정 운영.
  • 빠른 습득·변화 적응: AI 코딩 도구가 없던 시절에도 필요한 스택·기술을 스스로 적극 습득해 실무에 적용해왔고, 그 학습 경험을 바탕으로 지금은 AI 도구를 가장 효과적으로 활용하며 새 환경에 빠르게 적응.
  • 품질·안정성: 1,300개 이상의 단위 테스트 케이스와 CI/CD 자동 검증으로 운영 리스크 최소화, 빌드 시간(3분 내외) 최적화.
  • 주도적 문제 해결·업무 스케줄링: 비즈니스 목표와 영향도를 함께 고려해 우선순위를 스스로 판단하고 완수. 재직 기간동안 자격증 취득·학사·석사 과정을 병행하면서 동기간 내 조직 목표를 완수하기 위한 체계적인 팀원 관리 능력 입증.

인공지능을 전공한 백엔드 개발자

저는 인공지능을 전공한 백엔드 개발자입니다. 석사 과정에서는 모델을 직접 학습·평가하는 연구를 했고, 현업에서는 그 모델을 실제 서비스 파이프라인에 연동·운영해왔습니다. AI 기능이 제품에서 제대로 동작하려면 결국 데이터 파이프라인, API, 인프라 같은 백엔드의 기반이 탄탄해야 한다는 것을 현업과 연구를 병행하며 체감했습니다.

그래서 제게 인공지능 전공은 백엔드 커리어와 분리된 길이 아니라, AI 기능을 실제 제품에 녹여낼 수 있는 백엔드 개발자라는 강점으로 이어집니다. 실제로 최근 프로젝트에서는 Gemini·Grok 등의 모델을 PDF 파싱·콘텐츠 생성 파이프라인에 직접 연동해 운영했습니다.

1. LLM·생성형 AI를 제품에 녹여낸 경험과 개발 환경 자동화

반복적이고 정형화된 업무는 자동화하고, 사람은 더 중요한 문제에 집중해야 한다고 생각합니다. 저는 이 생각을 도구를 계속 진화시키며 실천해왔습니다. 처음에는 ChatGPT·GitHub Copilot으로 단순 편의 스크립트를 만드는 수준이었지만, 이후 Cursor로 로컬 파일 생성 자동화를 구현하고 여러 AI 도구를 도입·실험한 끝에 최근에는 Claude Code로 운영 업무까지 자동화했습니다. 도구를 단순히 가져다 쓰는 데 그치지 않고, 어떤 작업에 어떻게 적용하고 검증할지를 직접 설계하며 일합니다.

제품에서도 LLM을 직접 응용했습니다. ProblemShorts에서는 Gemini API로 PDF 문제를 파싱·전산화하는 적재 파이프라인을 구축해 1,000문제 기준 약 80시간 걸리던 수작업을 20분 내로 단축했고(총 2.3만 문제 중 1.3만 건을 2주 만에 적재), Grok과 이미지 생성 AI로 문제 해설 숏폼과 삽화 생성을 자동화했습니다. LLM을 데이터 파이프라인·콘텐츠 생성에 실제로 연동·운영해 본 경험이 제 가장 큰 강점입니다.

2. 대용량 트래픽을 위한 분산 아키텍처

안정성은 서비스의 신뢰도와 직결되기에, 대용량 트래픽을 소화하는 시스템을 설계하는 능력은 백엔드 개발자의 필수 역량이라고 생각합니다.

투스카이에서는 DAU 8천 명, MAU 2.8만 명, 총 회원 10만 명 규모의 라이프스타일 서비스 SANDI를 리뉴얼 구축·운영했습니다. 이 서비스는 출퇴근·점심·우천 등 사용자가 한꺼번에 몰리는 피크 시간대가 뚜렷해, 예측 가능한 최대 트래픽을 기준으로 용량을 산정하고 캐싱·인덱싱 전략을 맞췄습니다. 나아가 가장 극단적인 상황인 재난 시 비상대피 시스템에서는 데이터 처리량이 급증하는 경우를 가정한 부하테스트 시나리오를 설계하고, 그 결과를 인프라 담당과 함께 분석해 병목 지점을 찾고 서비스별 Auto Scaling 설정을 최적화했습니다. 회원 정보처럼 실시간성이 필요한 데이터는 인덱싱 중심으로 튜닝하고, 캐싱이 가능한 영역에는 캐시를 적극 활용하는 등 데이터 특성에 맞는 전략을 구분해 적용했습니다.

3. 다양한 데이터베이스와 테스트로 지키는 품질

서비스가 커질수록 데이터 특성에 맞는 저장소를 고르고, 변경이 기존 기능을 깨뜨리지 않도록 지키는 일이 중요해집니다. SANDI의 MSA 구조에서는 메인 페이지가 호출하는 8~9개 API가 공통으로 거치는 회원 정보 조회 쿼리를 인덱싱 중심으로 최적화했고, 주력인 PostgreSQL·MySQL 외에 로그 분석에서 ELK(Elasticsearch)를 사용해보며 데이터 성격에 따라 저장소를 달리 선택하는 감각을 키웠습니다.

또한 운영 중인 서비스에 기능을 더할 때 영향도를 매번 수작업으로 확인하던 비효율을 겪으며 단위 테스트를 습관으로 만들었습니다. ProblemShorts에서는 Application Layer 단위 테스트 1,300개 이상을 운영했는데, 테스트가 늘며 Spring Context 로딩이 빌드를 지연시키자 Context 로딩 없이 Mockito 기반으로 검증하도록 표준화한 커스텀 어노테이션을 직접 만들어 빌드 시간을 3분 내외로 유지했습니다. 테스트와 CI를 통해 QA 단계의 결함을 줄이고, 상용 배포를 주 1회 안정적으로 이어갔습니다.

4. 협업과 업무 조율

혼자 빨리 끝내는 것보다 함께 일하는 사람들이 막힘없이 움직이게 만드는 것이 결과를 더 크게 바꾼다고 생각합니다. 그래서 일을 시작할 때 누가 무엇을 언제까지 해야 하는지, 서로의 일이 어디서 맞물리는지를 먼저 맞춥니다.

투스카이에서는 비상대피 시스템 부하테스트 결과를 인프라 담당과 함께 분석해 병목을 찾고 서비스별 Auto Scaling 설정을 맞췄고, 임직원 복지몰·구내식당 등 7개 이상의 외부 시스템을 연계하며 각 시스템의 연동 방식과 일정을 상대 측과 조율했습니다.

아카교육과 아카소프트에서는 개발과 운영이 함께 있는 4~6인 팀에서 일했습니다. 직군이 달라도 같은 목표를 보도록 2주 단위 스프린트로 업무를 나누고 진척과 막힌 지점을 함께 확인했으며, 분기마다 1:1로 OKR을 세워 팀 목표와 각자의 목표가 어긋나지 않게 했습니다. 누가 맡아도 같은 기준으로 일할 수 있도록 업무 매뉴얼을 만들었고, 서로의 기여를 서로가 평가하는 동료평가 방식을 도입했습니다. 초기 모델의 운영 데이터와 마케팅 검토 결과가 기대와 달랐을 때는 개발·운영·마케팅 관점을 한자리에 놓고 리뉴얼을 결정했고, 6인 팀이 역할을 나눠 1개월 만에 완수했습니다. 그 1년 동안 퇴사자 없이 팀워크를 유지했습니다.
